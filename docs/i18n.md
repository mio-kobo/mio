# CLI localization and terminal themes

Mio 2.1.2 introduces one localization catalog shared by the native CLI (Core and
Full) and the Go reference CLI. The catalogs are compiled into the executable:
Mio never contacts a translation service, never reads a remote resource, and
never requires Python, Node.js or another runtime at execution time.

## Architecture

```
selfhost/i18n/locales/*.json     one complete catalog per BCP 47 locale
selfhost/i18n/languages.json     language list, primary locale, aliases, scripts
        │
        ├── scripts/i18n/catalog.py generate
        │       ├── selfhost/i18n/messages_generated.mio   native lookup tables
        │       └── internal/i18n/messages_generated.go    Go reference tables
        │
        ├── selfhost/i18n/i18n.mio    BCP 47 normalization, fallback, detection
        ├── selfhost/term/theme.mio   semantic color roles and terminal policy
        └── internal/i18n/i18n.go     the same contract for the Go CLI
```

The JSON catalogs are the single source of truth. `messages_generated.mio` and
`messages_generated.go` are committed so a release build needs no generator, but
CI regenerates them and fails if the committed copies are stale. Every catalog
has the same keys, the same `{0}` placeholders and the same technical tokens.
Adding a CLI string without adding it to every catalog is a CI failure.

Native code selects messages with a generated key constant
(`i18n.key_help_usage`) and substitutes arguments with `i18n.format`, so word
order is free to differ between languages. Go code uses `i18n.Format` and the
same key constants. Unknown keys and missing translations fall back to `en-US`
and finally to the key itself; a malformed catalog can never prevent startup.

### Why JSON and generated code?

* Reviewing a translation is a small, isolated diff.
* Incremental translation does not require recompiling the compiler.
* A static checker can compare placeholders and technical tokens without
  executing the CLI.
* The final user distribution is still a single offline binary.

## BCP 47 tags and fallback

Tags are canonicalized before lookup:

| Input | Canonical |
|---|---|
| `en-us`, `en_US.UTF-8` | `en-US` |
| `zh_cn` | `zh-CN` |
| `pt_br` | `pt-BR` |
| `zh_hant` | `zh-Hant` |

The fallback chain is:

1. The exact supported locale.
2. A regional alias from `languages.json` (`zh-MO` → `zh-HK`).
3. A script default (`zh-Hant` → `zh-TW`, `zh-Hans` → `zh-CN`).
4. The primary locale of the language (`fr-CA` → `fr-FR`, `de-AT` → `de-DE`,
   `en-AU` → `en-US`).
5. `en-US`.

Legacy aliases are accepted: `no` → `nb`, `iw` → `he`, `in` → `id`,
`tl` → `fil`, `mo` → `ro`. An unknown language, `C` or `POSIX` resolves to
`en-US`; it never aborts the command.

## Language selection priority

The native CLI resolves the current language once at startup:

1. Explicit `--lang <locale>` or `--lang=<locale>`.
2. `MIO_LANG`.
3. `LANGUAGE` (first item), then `LC_ALL`, `LC_MESSAGES`, `LANG`.
4. The operating-system preference.
5. `en-US`.

`--lang` is accepted before or after the command. Everything after `--` is a
program argument and is never interpreted as a Mio option.

```sh
mio --lang ja-JP help
mio help build --lang zh-CN
mio test . --lang=de-DE
mio run main.mio -- --lang is-a-program-argument
MIO_LANG=fr-CA mio --version
```

### Operating-system detection

* **macOS:** when no locale environment variable is set, the native CLI reads
  the `AppleLanguages` preference through `/usr/bin/defaults`. The helper is
  killed after a one-second deadline and any failure is ignored.
* **Windows:** the native CLI reads
  `HKCU\Control Panel\International\LocaleName` through `reg.exe`, with a
  PowerShell `Get-Culture` fallback. Both probes use the same bounded helper.
* **Linux and other Unix systems:** `LANGUAGE`, `LC_ALL`, `LC_MESSAGES` and
  `LANG` are authoritative. As a last resort `/etc/locale.conf` and
  `/etc/default/locale` are read for `LANG=`/`LC_ALL=`.

The Go reference CLI implements the same environment priority and fallback
normalization. It does not run platform helper processes; the native CLI is the
shipped user-facing binary.

Language detection is deliberately best-effort. A missing helper, a malformed
preference file or a denied process start resolves to `en-US` and never blocks
the command.

## Help and themes

`mio help` lists real commands in six groups: General, Compilation, Execution,
Diagnostics, Testing and Development tools. `mio help <command>` renders a
distinct page with that command's usage, options and examples. Help follows the
terminal width from `COLUMNS` (20–1000); when it is unset the width is 80.

Color is attached to semantic roles, not to translated strings:

| Role | Used for |
|---|---|
| title | version heading and section headings |
| command | command names |
| option | option syntax |
| success | passing test status |
| warning | skipped tests and warnings |
| error | failures and diagnostics |
| muted | group labels and secondary hints |
| description | default foreground text |

`--theme=auto|dark|light` selects the palette. `auto` consults `MIO_THEME`, then
`COLORFGBG` when the terminal publishes it. If no reliable background hint is
available it does **not** guess: it uses the high-contrast ANSI 16-color roles so
the terminal's own light/dark palette decides the final contrast. Explicit
`dark`/`light` palettes use ANSI 256 colors or True Color when
`COLORTERM=truecolor`/`24bit` advertises it.

### Color precedence

From highest to lowest:

1. `--color=always` / `--color=never`.
2. `--color=auto` (the default).
3. `NO_COLOR` non-empty, `TERM=dumb`, `CLICOLOR=0`: disable.
4. `CLICOLOR_FORCE` non-empty and not `0`: enable.
5. `CI` non-empty: disable for readable logs.
6. The target stream is a character device: enable; otherwise disable.

The exit code and the bytes of machine-readable output do not depend on any of
these settings.

### Terminal support

| Terminal | Colors | Theme detection |
|---|---|---|
| ANSI 16-color terminal | semantic 16-color roles | `COLORFGBG` when present; otherwise neutral |
| ANSI 256-color (`TERM=*256color`) | 256-color roles for explicit themes | `COLORFGBG`/`MIO_THEME` |
| True Color (`COLORTERM=truecolor`/`24bit`) | RGB roles for explicit themes | `COLORFGBG`/`MIO_THEME` |
| `TERM=dumb` | none | not queried |
| redirected output / CI | none by default | not queried |
| `NO_COLOR` | none unless `--color=always` | not queried |

Mio never writes a terminal query sequence (OSC 11, device-status requests) and
never waits for a terminal reply. This is why unsupported terminals cannot hang
the CLI and why `auto` sometimes chooses neutral ANSI colors instead of a
guessed background.

## Machine-readable output

The following stay byte-stable and are never localized or colored:

* `--format=json` diagnostics and test reports;
* JSON field names, status enums and schema version;
* LSP `Content-Length` frames and protocol fields;
* error codes such as `E_OPTIONS`, `E_TARGET`, `E_IO`, `E0602`;
* file paths, symbol names, command identifiers and Mio language keywords;
* the `mio v2.1.2-dev (...)` version string consumed by release tooling.

`--color=always` does not color JSON. `--lang` changes only natural-language
text. A CI job or IDE that parses JSON or LSP output is unaffected by the user's
language.

## Adding a language

1. Add the language and its primary locale to `selfhost/i18n/languages.json`.
2. Copy `selfhost/i18n/locales/en-US.json` to `<tag>.json`, translate every
   value, keep every key and every `{0}` placeholder, and set `"locale"` and
   `"direction"`.
3. Run `python3 scripts/i18n/catalog.py generate`.
4. Run `python3 scripts/i18n/catalog.py check --check-generated` and
   `python3 scripts/i18n/test_catalog.py`.
5. Test the native CLI: `mio help --lang <tag>`, `mio help build --lang <tag>`,
   and `mio test . --lang <tag>`.

Technical names (`Mio`, `Bunko`, `Mochi`, `Native AOT`, `BCP 47`), option
spellings, platform targets and command identifiers must stay untranslated.
Products are never localized.

## Known limitations and review items

* Translations are AI-assisted first drafts reviewed by the static checks
  described above. Native-speaker review is still welcome, especially for
  Japanese keigo, Arabic/Hebrew/Persian terminal bidi layout, Thai spacing and
  Indic terminology.
* RTL descriptions are emitted as plain Unicode text without invisible bidi
  control characters. Command and option columns remain literal ASCII, so most
  terminals display them left-to-right while the description flows RTL.
* Compiler-emitted diagnostic details (type names, source snippets, runtime
  trap text) remain in their existing English/technical form. CLI-level labels
  and the `cause:` label are localized.
* External Bunko resolution errors and filesystem errors reported by the
  standard library are technical strings and are not translated.
* The Go reference CLI does not probe the operating-system preference; use
  `--lang`, `MIO_LANG` or the standard locale environment variables with it.
* Windows `reg.exe` and PowerShell output encodings vary between releases; the
  native probe validates UTF-8/UTF-16 and falls back silently.

## Tests

```sh
python3 scripts/i18n/catalog.py check --check-generated
python3 scripts/i18n/test_catalog.py
go test ./internal/i18n ./cmd/mio
MIO_LANG=en-US mio test selfhost/... --format=json
```

The catalog tests check coverage, duplicate and empty messages, placeholders,
ANSI/control characters, bidi controls, technical tokens, RTL metadata,
English-variant distinctness, generation determinism and every catalog key's
CLI reference. The help/theme tests cover global and subcommand help, light and
dark palettes, no-color mode, non-TTY output, narrow widths and unknown
subcommands.
