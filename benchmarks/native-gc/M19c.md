# M19c：LOS、内部自动预算和压力快照

独立验收记录见 [m19c-acceptance.json](m19c-acceptance.json)。M19b 的历史状态、超时日志、报告和固定点哈希保持不变。M19c 功能验证与整体 M19 发布门禁分开判定；没有完整 Race 通过结果时，不解除发布阻塞。

## 地址和布局

普通对象沿用 16 字节对象头，Payload 仍按 16 字节对齐。Go Heap 的对象起点仍为 `heap+64`，元数据为固定 `end`；Mio 对象起点仍为 `metadata+3072`，元数据位于对象区之前。普通对象的 Side Metadata 地址公式分别是：

- Go：`end + 3072 + header - origin`。
- Mio：`end + header - origin`。

这两个公式中的 `end` 始终是预留对象区的末端，扩展可写前缀不会移动它。Side Metadata 仍预留与对象区容量相等的虚拟地址范围，按需开放页访问和触碰对象起点条目。

`align16(payload_bytes+16) >= threshold` 的请求走独立 LOS；默认阈值 128 KiB，元数据偏移 2592 的内部配置值 0 表示默认值。两个后端都读取该配置。

LOS 每个映射具有如下前缀，映射长度向 Darwin ARM64 的 16 KiB 页对齐：

| 相对映射起点 | 内容 |
| --- | --- |
| 0 | 全部 LOS 映射链的 next |
| 8 | 完整映射长度 |
| 16 | Young 链 next |
| 24 | Remembered 链 next |
| 32 | 原有对象头：type、flags、payload length |
| 48 | 原有 Payload |

LOS 的 Side Metadata 等于 `header-16`。分类器对 Arena 范围外的候选值仅在匹配某个 LOS 的精确 Payload 起点后读取对象头。大对象不搬迁；Storage、TypedArray、Closure、Cell 等沿用原来的精确布局和引用标志。数值缓冲区不会按字节或地址形状猜测引用。

LOS 进入同一个 Young 链、Remembered Set 和晋升协议。Minor 可以确认并回收不可达 Young LOS，Major 回收不可达 Old LOS。确认死亡后先移除可达性相关链接、清除 type，再进入释放阶段；普通 GC 每次最多尝试 8 次 `munmap`，剩余死亡映射继续收费并在后续 GC 重试。失败的 `munmap` 保留映射所有权。当前采用单线程有界同步释放，没有异步释放线程。显式销毁在安全退出阶段释放全部 LOS。

## 预算和扩展

现有 `HeapCapacity` / `-heap-mib` 仍表示统一对象占用上限：普通 Young/Old 与 Young/Old LOS 的对象头、Payload 和对齐都计入。没有增加公开 `--heap-max`。

新增内部 Go 选项 `AdaptiveHeap`、`HeapHardCap`，Mio lowering 提供 `compile_with_adaptive_heap` 和 `compile_with_memory_budget`。自动模式在 mmap 前读取 `hw.memsize` 和 DATA/AS 软限制；物理内存扣除 256 MiB 非托管余量后，以十二分之一作为对象预算候选，软限制扣除固定开销后以六分之一约束对象预算，再取请求上限的最小值并向页边界取整。查询失败使用保守的 16 MiB 对象候选；预算不足明确失败。当前对象区最大仍为 1 GiB。

默认托管 Hard Cap 是 `3 × round_page(object_capacity) + 64 KiB`。这是保守费用包络，覆盖普通 Arena 页、容量大小的 Side Metadata、固定元数据，以及完整 LOS 页映射。显式托管 Hard Cap 反推页对齐对象上限；真实分配仍同时检查对象上限和页费用上限。影子帧属于原生调用栈，代码、栈和其它非托管进程内存由非托管余量承担。

初始化只开放 `min(capacity,1 MiB)` 前缀；对象区和 Side Metadata 的空闲后缀使用 `PROT_NONE`。扩展按页调用 `mprotect`，不移动对象或元数据。扩展失败进入已有 Minor / Major 重试与独立 OOM 路径。不能把 Critical 状态当成分配成功或 OOM 错误处理。

GC 后的软目标为 `min(object_limit, max(1 MiB, 2×occupied + requested_span + rate_headroom))`，其中速率余量为约 50 ms 的分配量，最多四分之一对象上限。occupied 包括两代和 LOS。目标可以收缩；普通 Arena 的已开放前缀保持高水位，不在本阶段自动回收普通 Arena 页。LOS 死亡映射按有界释放策略归还。

以下量分别记录：

- Reserved：实际页取整的 Arena、Side Metadata、固定元数据和 LOS 虚拟映射总长。
- Committed：已开放前缀高水位和 LOS 完整映射的**保守托管页费用**，固定页开销及页面共享按上界收费，并以 Reserved 截断；它不是 OS 精确驻留页计数。
- Occupied：尚未被回收的对象物理跨度，包括头和填充。
- Goal：触发 GC 和增长的软目标。
- Hard Cap：包含托管元数据的费用硬上限。
- RSS：基准以每个子进程 `wait4` 的峰值 RSS 单独测量，包括代码、栈等非托管部分。

## 压力状态和共享策略代码

`Normal=0 / Elevated=1 / High=2 / Critical=3`。对象占用率的初始实验界线为 70/85/95%；还结合托管页费用、约 250 ms 的分配耗尽预测、最近低回收效率和系统压力。分配速率乘法具有饱和保护。系统压力每至少 10 ms 查询一次 `kern.memorystatus_vm_pressure_level`，查询不可用时显式标记 unknown，不假装系统正常。等级升级立即发布，下降必须在三个独立采样周期持续确认。

压力 reason 位：对象容量 1、页费用 2、速率预测 4、低回收效率 8、系统压力 16。[Apple 的内存压力通知说明](https://github.com/apple-oss-distributions/xnu/blob/main/doc/vm/memorystatus_notify.md) 是系统信号背景资料。

只读 `memory.snapshot(metadata,native_destination)` 复制 8 个 uint64：level、reason、heap_used、heap_committed、heap_limit、allocation_rate、gc_active、sequence。返回值不别名可变策略状态。Sequence 使用写入前后的奇偶发布约定；当前没有原子操作或内存屏障，**不构成多线程并发读写保证**。GC 不调用用户回调、不分配托管日志对象、不执行 HTTP 或接纳控制代码。

共享策略的符号 ARM64 模板在 `m19c_memory.go`；`go run ./scripts/native-memory-policy` 生成 `memory_policy.mio`，`--check` 检查同步。生成器只在开发维护时使用。原生 Stage 编译链的分支重定位和代码生成仍由 Mio 完成，不调用 Go。

High、Balanced、Low 预留同一配置槽和 Go 枚举，原生测试在三种配置值下检查同一可达对象的数据。M19c 不实现 M19f 调度器，也不改变任何精确扫描或写屏障规则。

## 重现

所有证据目录必须不存在，避免覆盖历史证据。

```sh
python3 scripts/validate-native-memory.py full --evidence build/my-m19c-full
python3 scripts/validate-native-memory.py race --evidence build/my-m19c-race
python3 scripts/validate-native-memory.py full-race --evidence build/my-m19c-full-race
python3 scripts/validate-native-memory.py mio --evidence build/my-m19c-mio
python3 scripts/probe-native-memory.py --evidence build/my-m19c-pure-probe
go run ./scripts/native-memory-policy --check
python3 -m unittest discover -s scripts -p 'test_benchmark_native_gc.py'
python3 scripts/check-native-aot-fixed-point.py --evidence build/my-m19c-fixed-point \
  --ci-ancestor 5d4c1dbdc75aba87e2213bec2b0031c4ff21f379 \
  --gc-witness --gc-witness-heap-mib 384
MIO_M18_EVIDENCE_DIR="$PWD/build/my-m19c-fixed-point" \
  go test ./internal/aot -run '^TestM18' -count=1 -v -timeout=30m
python3 scripts/benchmark-native-gc.py --evidence build/my-m19c-compare \
  --baseline-evidence build/m19b-20261021-benchmark-final --iterations 100 --warmups 2
python3 scripts/benchmark-native-gc.py --m19c --evidence build/my-m19c-specialized \
  --iterations 100 --warmups 2
```

纯 Mio 探针由 Mio emitter 构建并实际执行 Darwin ARM64 镜像，检查跨页数据、别名、Minor 回收、晋升、精确分类、四级压力和滞后恢复。探针构建器使用带标准库绑定的 Go VM 执行 Mio emitter；完整原生自举和差分则另行验证 Mio emitter 在原生编译器中运行。

## 限制和后续

- 当前速率耗尽预测偏保守；短命高吞吐分配即使能够持续回收，也可能出现 Critical。不能直接把本阶段等级作为生产接纳或 HTTP 限流决策。M19f 需要校准预测、时间尺度和费用策略。
- LOS 查询目前遍历映射链；释放采用每次 8 个的同步批次，没有并发释放保证。
- Committed 为预算上界，OS 精确物理提交/驻留页仍需额外探测；普通 Arena 页尚未随软目标收缩而去提交。
- 小对象路径增加压力计量和页预算检查，部分基准存在明显开销；全部样本和相同会话的历史对照都保留，不能据此声称所有负载性能改善。
- 没有进行破坏性宿主机缺内存实验；系统压力状态机使用可控原生输入验证，并验证正常宿主机查询。
- M19d 接纳控制、M19e 并发 Old GC、M19f 三档自动调优和多线程快照原子发布均未实施。
